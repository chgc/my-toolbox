# Clear Writing Style（通用受控語言寫作風格）

## 適用範圍（Scope）

- **套用在**：任何需要讀者快速、低成本理解的書面輸出——README、技術文件、規格書、SOP、API 文件、報告、email、教學、Slack／通訊訊息、AI 產生的一般文字。
- **一律不套用**：
  - **blog.kevinyang.net 的部落格文章 → 改用 `kevin-writing-style`**（兩者衝突時，部落格文章一律以 kevin-writing-style 為準）。
  - Obsidian 個人筆記（記給自己、求快求全的筆記，不適用）。
  - 行銷文案、社群吸睛貼文、需要強烈個人聲音的內容。
- 判斷方式：目標是「讓讀者以最低成本理解」→ 用本風格；目標是「展現個人風格 / 行銷」→ 不用。

## 背景

- 由 `content-clarity-style` 泛化而來：content-pipeline 專用版只服務 strategist → researcher → writer → editor → publisher 五個 agent；本 skill 是同一套規則的通用版，任何寫作場合都可用。
- 核心方法：改編 **ASD-STE100**（航空維修文件用的受控語言規範）。其約束恰好命中「可讀性」——少字、少歧義、少花樣。
- 刻意保留 **80% 的 dial**：STE 全開會變成機器語，所以分成「強制核心」與「可調鬆緊」兩層。

## 核心原則（Top 5）

1. **一句一事**：每個句子只講一件事，講完就換行。
2. **清楚 > 優雅**：任何為了「好聽」而存在的字都是噪音，先刪再說。
3. **同一個詞到底**：同一概念全篇用同一個詞，禁止同義詞換花樣。
4. **結論先行**：段落第一句就是答案，後面才是解釋。
5. **寫不順就換載體**：一段文字寫超過 2 段還在繞，改用 diagram / table / code block。

## 強制核心（Mandatory，不可關閉）

這些規則零成本、高收益，任何主題都適用：

1. **句子長度上限**：中文 ≤ 40 字、英文 ≤ 20 個詞；超過就拆成兩句。
2. **主動語態**：一律主動。`the conclusion was reached` → `we concluded`；`進行了分析` → `分析了`。
3. **去名詞化**：動詞名詞化（nominalization）改回動詞。`達成了一個共識` → `達成共識`；`make a decision` → `decide`。
4. **術語一致性**：每個概念全文只用一個詞——第一處用什麼，之後就用什麼。**立論時列一份「術語表」**（≥3 個關鍵術語時），後續文字凍結使用。
5. **刪修飾與過渡詞**：刪掉為順暢而存在的副詞、形容詞、`moreover / furthermore / 值得注意的是 / 值得一提的是 / 總而言之`。
6. **結論先行**：每段第一句 = 該段結論（topic sentence first），後續才是論據或細節。
7. **具體取代抽象**：「易於理解」→「每步只講一件事」；「高效能」→ 實際時間或數字。

## 80% Dial（可調鬆緊）

作者依主題在 80%~100% 之間調整，並在產出時註明採用的 dial（例如 `dial: 85%`、`關閉：修飾語完全清除`）：

| 規則 | 100%（STE 全開） | 80%（預設建議） |
|------|------------------|------------------|
| 動詞形式 | 只准簡單現在式/命令式 | 允許簡單過去式講案例 |
| 語氣 | 命令式為主 | 准許少數委婉語（`建議`、`可以考慮`） |
| 修飾語 | 全部禁止 | 每段 ≤ 1 個輕修飾語 |
| 結論先行 | 嚴格 | 長段落可先用 1 句鋪陳再給結論 |

## Format 維度（比 prose 更重要的規則）

**風格不只關乎字，也關乎載體。** 以下規則優先於寫作規則：

1. **超過 2 段還在解釋同一概念 → 換載體**：改用 table（比較）、code block（範例）、或 diagram（流程/關係）。
2. **可選第二 artifact**：每份文件可附一個「可丟棄的客製 artifact」——Mermaid diagram、HTML 互動頁。成本低、理解成本大幅下降。
3. **每次產出先給「載體建議」**：動手前先判斷該主題最適合 prose / diagram / HTML / 影片，並說明理由——這是「writing → diagram → webpage → video」階梯的最小落地版。
4. **每個 diagram 要有標題 + 一句話圖例**，不讓讀者自己猜圖在講什麼。

## 各階段檢查清單

### 寫稿時（草稿）
- [ ] 句子全部 ≤ 40 字（中文）？長句已拆？
- [ ] 全部主動語態？名詞化物已還原？
- [ ] 關鍵術語是否只有一個用詞？有沒有同義詞換花樣？
- [ ] 每段第一句就是結論？
- [ ] 有沒有任何概念繞了超過 2 段？→ 換載體或加 diagram。
- [ ] 註明採用的 dial（如 `dial: 80%`）。

### 修稿時（編輯）
- 刪：所有不影響理解的形容詞、副詞、過渡詞。
- 拆：所有超長句（編輯是句子長度的最後一道關）。
- 統一：抓出同義詞高頻替換，改回首現用詞。
- 檢查：每段是否結論先行；opening 是否 1 句點出主旨、closing 是否只留結論。

### 定稿時（排版/發送）
- 先給「格式建議」：prose / diagram / HTML 哪個最易懂 + 理由。
- 維持原內容與編輯決定，本 skill 只負責把 prose 換成更易懂的載體，不重新寫作。

## 與其他 skills 的關係

| Skill | 優先序 |
|-------|--------|
| `kevin-writing-style` | 部落格文章（blog.kevinyang.net）一律蓋過本 skill |
| `content-clarity-style` | content-pipeline 專用版；本 skill 是同一風格的通用版，兩者可並存 |
| `content-obsidian-pipeline` | 儲存相關；本 skill 只管寫作風格，不管儲存格式 |

## 一句話總結

> 把「讀者 parse 的成本」當成唯一 KPI：字能少就少、一句只講一件事、同一個詞用到尾；寫不順就換成 diagram / table / HTML——prose 不是唯一載體。
